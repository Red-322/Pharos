# Pharos V5.0 设计决策

> 本文档是 [`V5.0-项目文档.md`](V5.0-项目文档.md) 的补充，说明检索质量优化中的 5 个关键决策及其权衡。

---

## 5.1 双通道混合检索与 RRF 融合

### 为什么需要双通道

单一检索方式各有盲区：

| 通道 | 擅长 | 弱在 |
| --- | --- | --- |
| 向量（pgvector） | 语义相近、同义表达 | 专有名词、编号、精确短语 |
| 关键词（ES / BM25） | 术语、编号、精确命中 | 换个说法就检不到 |

企业知识库两类问题都有，所以两路都要。

### 为什么用 RRF 而不是加权求和

- 向量分是余弦相似度（0–1），ES 分是 BM25（没有固定上限），**量纲不同，直接加权没有可比性**；
- RRF 只看排名：`score = Σ 1/(k + rank)`，天然规避量纲问题；
- 代价是**丢掉分数信息**，所以 RRF 只能当粗排，后面必须接精排。

### 归一化

RRF 原始分很小（0–2 左右），用 `1 - e^(-raw)` 压到 0–1：

- 单调，不改变排序；
- 方便后续证据分级设阈值；
- 比 min-max 稳定：不依赖当前批次的最大/最小值。

### 权衡

- RRF 的 `k` 越大，名次间差距越小；项目取 `k=0`。
- 参数对照：`k=60` 时 Chunk Top5 从 85.0% 降到 82.5%（-2.5，抖动边缘），所以保留 0。

## 5.2 Rerank 精排：为什么必须在截断之前

### 双塔与交叉编码

| 方式 | 怎么算 | 速度 | 用在哪 |
| --- | --- | --- | --- |
| 双塔 | query 和文档分别编码，最后比向量 | 快（文档向量可离线算） | 召回 |
| 交叉编码 | query + 候选拼成一个输入，逐条打分 | 慢（每条都要推理） | 精排 |

一句话：**召回是海选，精排是面试。**

### 为什么不能先截断再精排

如果先截断到 Top5，再让 Rerank 在 5 条里选：

- 召回阶段漏掉的相关切片**永远回不来**；
- 精排只能在错误的候选集里挑，提升有限。

所以顺序必须是：

```
召回 Top50 → RRF 融合 → 候选池 20–50 → Rerank → 截断 Top5
```

### 结果与代价

- Chunk Top5：82.5–87.5% → **92.5%**
- MRR：0.69–0.72 → **0.813**
- 代价：**+286ms**

### 权衡

- 候选池越大，精排越准，但越慢；20–50 是延迟与效果的折中；
- Rerank 模型有 `top-n` 参数，实际生效值以调用参数为准，不能只看配置注释。

## 5.3 查询规划与分通道

### 三种策略

LLM 先判断问题形态，输出 `{strategy, queries}`：

| 策略 | 场景 | 行为 |
| --- | --- | --- |
| DIRECT | 问题明确 | 原句直接检索 |
| REWRITE | 口语化 | 改写成检索友好的短语 |
| DECOMPOSE | 复合问题 | 拆成多条子查询 |

### 为什么子查询只走关键词

- 子查询是 LLM 从原问题派生出来的，**已经做过一次语义展开**；
- 再走一遍向量检索，和原问题高度重复，**边际收益很低**；
- 关键词通道正好补专有名词、编号。

### 结果

- 优化前：平均 2.25 条查询 × 每条双通道 → 向量调用 **2.25 次/题**；
- 优化后：只有原始问题走向量 → **1 次/题**；
- 质量基本持平。

### 异常兜底

查询规划依赖 LLM，可能失败。失败时**降级为 DIRECT**，保证问答链路可用；降级会打日志，便于排查。

### 权衡

- 分通道省了向量调用，但依赖规划质量；
- HyDE（假设答案检索）实现了但**默认未启用**：规划修复后口语型只比关键词型低约 5 个点，而 HyDE 每题多一次 LLM 调用，性价比不高。

## 5.4 40 题配对评测集

### 为什么配对

同一知识点用两种问法：

- 关键词型：「RRF 融合排序的作用」
- 口语型：「两个检索结果怎么合到一起」

配对的作用：

- 口语型明显更差 → 检索对表达方式不够稳健；
- 两题都差 → 知识本身没召回到；
- 两题都好 → 这个知识点稳。

只看总分，分不清「检索不准」还是「提问风格差异」。

### 标注粒度

- `expectedDocumentId`：正确文档；
- `expectedChunkIndexes`：正确切片（chunk 级）；
- `difficulty`：EASY / MEDIUM / HARD；
- `questionType`：关键词型 / 口语型。

### 指标与抖动

| 指标 | 说明 |
| --- | --- |
| Doc Top1 / Top5 | 文档级命中 |
| Chunk Top5 | 切片级命中（更严） |
| MRR | 正确答案排名的倒数平均 |
| 耗时 | 单题检索平均耗时 |

40 题里 1 题 = 2.5 个百分点；差值在 ±3 题内不做过度解读。

### 权衡

- 样本只有 40 题，结论说「在这次对照里」；
- 标注到 chunk 级，**换语料或换切片参数会让标注失效**，需要重标。

## 5.5 四级证据分级与拒答

### 为什么不让模型自己判断

模型对「自己知不知道」容易过度自信；用检索侧的客观信号更稳定：

- 双通道命中标记：BOTH / VECTOR / KEYWORD；
- 归一化后的得分。

### 四级

| 级别 | 含义 |
| --- | --- |
| NONE | 两个通道都没命中 |
| WEAK | 只命中一个通道，或得分很低 |
| PARTIAL | 有命中，但证据覆盖不完整 |
| SUFFICIENT | 双通道命中、得分过阈值 |

不到 SUFFICIENT 直接拒答，不让模型硬编。

### 权衡

- 阈值太高 → 误拒；太低 → 幻觉；
- 用评测集调阈值，在「少编」和「少拒」之间取平衡。

## 5.6 关键取舍汇总

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 是否扫 chunk size | 不扫 | 改切片边界会让 40 题 chunk 级标注全部失效，重标代价大于收益 |
| 是否启用 HyDE | 默认不启用 | 天花板约 5 个点，多一次 LLM 调用，性价比不高 |
| 是否做语义缓存 | 不做 | 同义改写与不相关问题的相似度区间重叠（0.68 vs 0.54），零误判约束下命中率仅 30% |
| 是否做 HNSW 调优 | 暂不做 | 先用默认参数（m=16、ef_construction=200），优先保证链路正确 |

## 5.7 与 V4.1 的衔接

V5.0 不改变 V4.1 的 API、数据模型和权限体系：

- 问答接口、SSE 事件、`recordId` 保持不变；
- 变更集中在 `HybridChunkRetrievalService` 及其依赖的检索组件；
- 评测集与 `EvalRunner` 独立于主链路，不侵入 `src/main`。
