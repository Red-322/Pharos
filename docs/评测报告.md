# 检索质量评测报告

> **数据集**：40 题配对评测集（20 道关键词型 + 20 道口语型，两两配对）
> **位置**：`Pharos-backend/src/test/resources/eval/questions.json`
> **主指标**：**Chunk Top5**（正确切片是否进入上下文前 5）
> **结论**：**Rerank 把 Chunk Top5 从 82.5–87.5% 提到 92.5%，MRR 从 0.69–0.72 提到 0.813；邻居窗口 1、RRF k=0 保持默认。**

---

## 一、评测集设计

### 1.1 为什么配对

同一知识点用两种问法：

| 类型 | 例子 | 考什么 |
| --- | --- | --- |
| 关键词型 | 「RRF 融合排序的作用」 | 术语命中 |
| 口语型 | 「两个检索结果怎么合到一起」 | 语义理解 / 表达差异 |

**配对的作用**：

- 口语型明显更差 → 检索对表达方式不够稳健（换个说法就检不到）；
- 两题都差 → 知识本身没召回到；
- 两题都好 → 这个知识点稳。

只看一个总分，分不清是「检索不准」还是「提问风格差异」；配对能定位。

### 1.2 字段说明

| 字段 | 含义 |
| --- | --- |
| `id` | 题号，1–40 |
| `question` | 问题文本 |
| `expectedDocumentId` | 正确答案所在文档 ID |
| `expectedChunkIndexes` | 正确答案所在切片序号（chunk 级标注） |
| `difficulty` | EASY / MEDIUM / HARD |
| `questionType` | 关键词型 / 口语型 |
| `note` | 备注（可为空） |

示例：

```json
{
  "id": 1,
  "question": "双通道为什么合起来用？RRF有什么作用？",
  "expectedDocumentId": 6,
  "expectedChunkIndexes": [13],
  "difficulty": "EASY",
  "note": "",
  "questionType": "关键词型"
}
```

### 1.3 指标定义

| 指标 | 含义 |
| --- | --- |
| **Doc Top1 / Top5** | 正确答案所在的**文档**是否出现在前 1 / 前 5 个文档 |
| **Chunk Top5** | 正确答案所在的**切片**是否出现在前 5 个切片（比 Doc 更严） |
| **MRR** | 正确答案排名的倒数，取平均；越接近 1 越好 |
| **耗时** | 单题检索平均耗时（ms） |

**抖动**：40 题里 1 题 = 2.5 个百分点；差值在 ±3 题以内不做过度解读。

---

## 二、怎么跑

评测入口：`Pharos-backend/src/test/java/com/pharos/rag/eval/EvalRunner.java`

- 直连 `HybridChunkRetrievalService.retrieve()`，测的是共用检索底座；
- 读取 `questions.json`，逐题比对 `expectedDocumentId` / `expectedChunkIndexes`；
- 输出 Doc Top1 / Doc Top5 / Chunk Top5 / MRR / 耗时；
- 可按 `questionType` 和 `difficulty` 分组统计。

**原则**：每次对照只改一个变量，其余保持不变。

---

## 三、实验 1：Rerank 前后

**初始基线（Rerank 关）**：

| 指标 | 值 |
| --- | --- |
| Doc Top1 | 72.5% |
| Doc Top5 | 97.5% |
| Chunk Top5 | 87.5% |
| MRR | 0.692 |
| 平均耗时 | 1851ms |

**对照结果**：

| 配置 | Chunk Top5 | MRR | 耗时 |
| --- | --- | --- | --- |
| Rerank 关（3 次跑） | 82.5% – 87.5% | 0.69 – 0.72 | 基线 |
| Rerank 开（1 次跑） | **92.5%** | **0.813** | **+286ms** |

**结论**：

- Rerank 打开后，Chunk Top5 提升约 **5–10 个点**，MRR 提升约 **0.09–0.12**；
- 代价是 **+286ms**；
- Rerank 开只有单跑（额度所限），所以结论限定在「本次对照」。

---

## 四、实验 2：参数扫描（Rerank 关）

固定 chunk 240 / RRF 0 / 邻居 1，逐项改一个参数：

| # | 配置 | Chunk Top5 | Doc Top1 | Doc Top5 | MRR | 耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 基线 | **85.0%** | 75.0% | 92.5% | 0.720 | 1728ms |
| 1 | 邻居窗口 0 | **77.5%**（↓7.5） | 75.0% | 95.0% | 0.638 | 1690ms |
| 2 | 邻居窗口 2 | 85.0%（持平） | 77.5% | 95.0% | 0.732 | 1627ms |
| 3 | RRF k=60 | 82.5%（↓2.5） | 77.5% | 90.0% | 0.690 | 1609ms |
| 4 | 复跑基线 | **85.0%** | 72.5% | 95.0% | 0.707 | 1657ms |

> 这里的基线（85.0%）与实验 1 的初始基线（87.5%）不是同一次跑，差异在 ±2.5 抖动内。

**结论**：

1. **邻居扩展有用**：关掉（窗口 0）Chunk Top5 掉 7.5 个点，超过抖动 → 真下降；
2. **邻居窗口保持 1**：扩到 2 持平（在抖动内），没必要扩；
3. **RRF k 保持 0**：k=60 掉 2.5 点，刚好在抖动边缘，不能定论；k=0 至少不差；
4. **评测可复现**：复跑基线 Chunk Top5 完全一致（85.0%），其余差异在 ±2.5 内。

**⇒ 三个默认值都不用改，这本身就是一个结论。**

---

## 五、抖动与局限

- **抖动 ±2.5 个点**：40 题里 1 题 = 2.5 个百分点；
- **抖动来源**：查询规划每次调 LLM，生成的改写短语不完全一致；
- **样本小**：40 题，标注由一人完成；
- **Rerank 单跑**：只说「在这次对照里」提升，不宣称线上必涨；
- **环境绑定**：`expectedChunkIndexes` 是硬编码的，换语料或换切片参数要重标。

---

## 六、维护规则

1. **换语料 / 换切片参数 → 标注全部失效**：`expectedChunkIndexes` 是硬编码的，切片边界一变就要重标；
2. **新增题目要成对加**：一个关键词型 + 一个口语型，覆盖同一知识点；
3. **不要用这套题调参又当验收**：调参看趋势，验收另留一批题；
4. **样本只有 40 题**：结论说「在这次对照里」，不宣称线上一定提升。

---

## 七、总体结论

| 改动 | 效果 | 是否保留 |
| --- | --- | --- |
| Rerank 精排 | Chunk Top5 +5–10 点，+286ms | ✅ 保留 |
| 查询分通道 | 向量调用 2.25 → 1 次/题，质量持平 | ✅ 保留 |
| 邻居窗口 | 关掉 -7.5 点；扩到 2 无收益 | ✅ 保持 1 |
| RRF k | k=60 -2.5 点（抖动边缘） | ✅ 保持 0 |
| chunk size 扫描 | 会使 chunk 级标注失效 | ❌ 不做 |
| HyDE | 天花板约 5 点，多一次 LLM 调用 | ❌ 默认不启用 |
| 语义缓存 | 相似度区间重叠，零误判下命中率 30% | ❌ 不移入 |
